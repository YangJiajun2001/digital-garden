### 知识点总结与分类

*   **[概念类]**
    *   Token 刺客：那些让 Token 消耗在不知不觉中失控的操作习惯与场景
    *   上下文滚雪球：多轮对话中历史消息累积，使每轮成本呈指数级增长
    *   工具 Schema 开销：挂载过多 MCP 工具时，每轮对话光工具定义就要烧掉数千 Token
*   **[技术类]**
    *   上下文工程：控制喂给模型的输入范围，避免「大文件 + 深层依赖」成为 Token 黑洞
    *   会话边界管理：任务完成即开新会话，把关键信息沉淀为文件而非留在上下文
    *   重试成本控制：AI 无成本感知，重试自带完整失败记录，越试越贵
*   **[应用类]**
    *   固定流程脚本化：批量重复任务用脚本替代逐条 Prompt，图片类目识别才交给 Agent
    *   模型分级分工：梳理信息用高质量模型输出 md，细节文件操作交给便宜模型
    *   止损动作「断」：发现 Agent 跑偏立即中断，比事后看账单更省钱

## 引言

月底看 Token 账单的那一刻，很多人的心情就像被刺客背刺：明明只是改了个小 Bug、挪了个文件路径、问了句「顺便看看还有没有问题」，消耗却比一个完整功能开发还要夸张。**Token 刺客从不是「大任务」的专利，它们往往藏在最不起眼的小操作里。**

这篇文章汇总了腾讯内部 12 位同学的真实踩坑记录（来自 CSIG 技术委员会 & 内部社区 KM），我们把它们归类、剖析根因，并提炼出可落地的止损技巧。读完之后你会发现：**大部分 Token 浪费不是模型的问题，而是上下文工程和操作习惯的问题。**

## 一、三类最典型的 Token 刺客

先快速浏览 12 个案例，绝大多数可以归入以下三类：

**① 输入侧失控：喂得太多**

> 案例 1：只想改个前端组件样式，把整个 src 目录都喂进去了，AI 把 i18n 文案、mock 数据全读了一遍，吐出一堆不需要动的代码。
> 案例 2：重构一个组件，本来只想改样式逻辑，结果 AI 把 hooks、utils、类型定义全扫了一圈，改动 5 行代码，烧了 3 万 Token。
> 案例 7：Agent 一启动就开始扫仓库、历史代码、接口定义、配置文件，「找上下文」烧掉一大截 Token，真正要改的只有几十行。
> 案例 10：排查接口超时，把整段请求日志贴进去，几千行无关框架打印全被吞了，来回三轮 Token 破十万，最后定位到的问题就一行配置写错。

**② 上下文失控：历史越滚越大**

> 案例 3：任务卡死中断后换模型说「继续任务」，结果该对话积压了几百条消息，Agent 根本不知道继续什么，只能在噪音里重新回顾上下文。
> 案例 5：上下文污染太多，每次提问模型都要回顾一遍所有上下文，即使后续需求很简单，消耗也异常高。
> 案例 6：让 AI 反复修改一个很长的 md 文件，每次它都要从头读一遍，上下文理解上烧掉大量 Token。
> 案例 8：Agent 跑长任务，第 1 轮 2k Token，第 20 轮可能 50k+，后面每一步的成本是前面的十几倍，但真正有用的上下文就最近三轮。

**③ 行为失控：指令太模糊 / 重试太任性**

> 案例 4：「顺便帮我看看还有没有别的问题」——本来两分钟改完的 Bug，AI 一路检查整个模块、顺手优化、分析调用链，Token 已经飞了。
> 案例 8：出错了让它自己重试，AI 没有成本感知，每次重试都带着完整的失败记录，越试越贵。
> 案例 11：只是想挪动一个文件路径，被刺了。

## 二、疑难点深度解析：为什么「小改动」反而最烧钱？

**所需基础知识：**

> 在深入本节之前，建议你先了解两点：一是 **LLM 的注意力机制与上下文窗口**——模型每一轮都要重新处理全部上下文，Token 消耗随上下文长度线性/超线性增长；二是 **Agent 的「规划—执行—观察」循环**——每一步工具调用都会把新结果追加进上下文，形成滚雪球效应。

**由浅入深的解释：**

**第一步，先理解成本结构。**一次 Agent 对话的 Token 消耗主要由三部分组成：

```text
总消耗 = 输入 Token（上下文 + 工具调用） × 轮数 + 输出 Token × 轮数
```

其中**输入 Token 是真正的大头**。每一轮交互，模型都要「重读」一遍整个历史上下文。也就是说：上下文越长，单轮就越贵；轮数越多，重复读的次数就越多——两者相乘，成本呈指数级爆炸。

**第二步，理解「小改动烧大钱」的机制。**小改动本身只产生几十行输出，贵的是它前面的「找上下文」过程：

- **大文件 + 深层依赖是黑洞**：一个组件背后可能挂着 hooks、utils、类型定义、接口文档。Agent 为了「稳妥」，倾向于把相关文件全部读入，每次读取都是一次完整的文件内容进上下文。
- **模糊指令放大搜索范围**：「顺便看看还有没有别的问题」「你自己找文件呗」这类指令，等于授权 Agent 无限扩大探索边界。它读得越多，下一次判断可依据的信息就越多，于是更倾向于继续读——**这是一个自我强化的正向反馈，直到上下文塞满。**

**第三步，用数学直观感受滚雪球。**假设每轮新增有用信息约 2k Token，但每轮都要重读全部历史：

| 轮数 | 上下文长度 | 该轮输入消耗 | 累计输入消耗 |
| ---- | ---- | ---- | ---- |
| 第 1 轮 | 2k | 2k | 2k |
| 第 10 轮 | 20k | 20k | 110k |
| 第 20 轮 | 50k | 50k | 470k |

**真正有用的上下文往往只有最近几轮**，但每轮都在为前面所有轮的「历史噪音」付费。这就是「第 20 轮的成本是第 1 轮的十几倍」的原因。

**示例：**

用一个简单的代码示例来模拟「无用历史对成本的放大」：

```python
def estimate_context_cost(history: list[dict], token_price: float = 0.02) -> float:
    """
    估算一次多轮 Agent 对话的总输入成本。
    history: [{"role": "user", "content": ...}, {"role": "assistant", "content": ...}, ...]
    核心逻辑：每一轮都要重读全部历史，成本随轮数指数累积。
    """
    total_tokens = 0
    for i in range(1, len(history) + 1):
        # 第 i 轮：模型重读前 i 条历史（含本轮新内容）
        context = history[:i]
        tokens_this_round = sum(len(m["content"]) for m in context)  # 简化：字数 ≈ token 数
        total_tokens += tokens_this_round
        print(f"第 {i:>2} 轮: 上下文 {tokens_this_round:>6} tokens, 累计 {total_tokens:>8}")

    cost = total_tokens * token_price / 1000
    print(f"总输入成本 ≈ ¥{cost:.2f}")
    return cost

# 假设 20 轮对话，每轮新增 2k 字符
history = [{"role": "user", "content": "x" * 2000} for _ in range(20)]
estimate_context_cost(history)
```

**结论：** 控制 Token 消耗的核心，不是让模型「写得更省」，而是**控制上下文的长度和轮数**——这正是上下文工程要解决的问题。

## 三、实战止损技巧：从 12 个案例中提炼的规则

### 技巧一：一个「断」字诀——发现跑偏立即掐断

> 案例 1 的同学总结：发现不对劲立马掐掉，比月底看面板的时候心疼强。

Agent 一旦开始「自我修正」，往往会越修越离谱——每轮重试都带着完整失败记录，噪音叠加噪音。**止损的黄金时间是「发现跑偏的第一秒」。**

### 技巧二：小改动也要先收窄输入边界

- 明确告诉 AI 只读哪些文件，而不是让它「自己找文件」。
- 排查问题不要贴整段日志，先截取与错误相关的片段，或先让脚本把无关行过滤掉。
- 大文件先定位到相关函数/行号，再让 AI 基于局部上下文工作。

### 技巧三：长任务拆段跑，做完一段开新会话

上下文越长，单轮越贵。**每完成一个里程碑，就把关键信息沉淀成一个文件（如 `CONTEXT.md`），然后开新会话**，新会话只携带这份精简上下文，而不是几百条历史消息。

### 技巧四：别让 AI 说「继续任务」

中断后换模型直接说「继续任务」是最大的坑——它根本不知道继续什么，只能在噪音里重新回顾。**正确的做法是：把已完成的部分、当前状态、剩余目标写成一个清晰的状态文件，再开新会话。**

### 技巧五：同一问题重试不超过 2 次

AI 没有成本感知，会一直试下去。设定硬规则：**同一个问题重试超过 2 次，停下来问人。** 人为判断往往 30 秒就能指出方向错误，远比让 AI 试第 5 次便宜。

### 技巧六：控制工具挂载数量

同时开 20 多个 MCP，每轮对话光工具 schema 就烧掉 3-5k Token——什么活没干，钱先没了。**只挂当前任务需要的工具**，成本可砍掉一大半。

### 技巧七：固定流程脚本化，Agent 只做「非标」

上千个商户逐条喂给大模型判类目、规则重复喂上千遍——这种可枚举、可重复的批量任务应该写成脚本，Agent 只处理图片类目识别这类非结构化任务。

### 技巧八：按任务类型分级使用模型

4-5 页 Word 文件操作烧 20-30 元，而同样的模型整理数据输出 md 只花 2-3 元。**先让高质量模型完成信息梳理（输出 md），再让便宜模型执行细节文件操作**——贵的模型管思考，便宜的模型管执行。

## 四、一张表总结：Token 刺客的识别与对策

| Token 刺客 | 典型信号 | 止损对策 |
| ---- | ---- | ---- |
| 全目录喂食 | AI 读了一堆无关文件 | 显式限定文件范围 |
| 大文件 + 深层依赖 | 改动 5 行，烧 3 万 Token | 定位函数/行号，局部上下文 |
| 日志/长文全量粘贴 | 无关内容被吞进上下文 | 先过滤，再投喂片段 |
| 上下文滚雪球 | 单轮成本随轮数暴涨 | 里程碑拆段，关键信息落文件 |
| 中断后「继续任务」 | Agent 在噪音里瞎回顾 | 写状态文件，开新会话 |
| 「顺便看看」式指令 | 探索边界无限放大 | 先解决当前问题，再开新会话 |
| 无成本感知的重试 | 越修越离谱 | 重试超过 2 次，停下来问人 |
| MCP 挂太多 | 每轮白烧 3-5k Token | 只挂当前任务所需工具 |
| 批量任务逐条喂 Prompt | 规则重复喂上千遍 | 写脚本跑固定流程 |
| 昂贵模型做粗活 | Word 操作 20-30 元/次 | 贵模型梳理、便宜模型执行 |

## 小结

回顾全部 12 个案例，最深的体感是：**Token 刺客的本质，是上下文工程的失控。** 每一次「顺手」「顺便」「反正它聪明」的背后，都是把决策权——以及账单——交还给了没有成本感知的 AI。

好在对策并不复杂，核心就是两条：

- **管住输入**：收窄文件范围、过滤噪音、沉淀关键信息为文件。
- **管住行为**：及时中断、限次重试、拆段开新会话、任务分级。

**你管理上下文的纪律，就是你的 Token 预算。**

### 延伸思考与创意展望

基于以上讨论，我们可以进一步思考以下方向：

1.  **「Token 预算」作为一等公民进入 Agent 协议**：未来的 Agent 框架是否应该内置成本感知——在规划阶段就估算每一步的 Token 开销，超预算时主动询问用户而不是继续执行？类比数据库的查询计划器，Agent 的「执行计划」同样可以带成本估计，让「继续」和「重试」都先亮出价格牌。

2.  **上下文压缩的商业化机会**：案例反复证明「最近三轮之外的历史基本都是噪音」。一个专注于**语义级上下文压缩**的工具（把 50k Token 的历史无损压缩为可检索的 5k Token 摘要，且支持按需回溯细节）将具有巨大价值——它本质上是给 LLM 装了一个「遗忘但可检索」的记忆系统。

3.  **开放性问题：当 Token 成本趋近于零，「上下文工程」还会是一门必要的技能吗？** 如果未来模型上下文窗口无限大且推理成本极低，那么「精简输入、拆段会话」这些纪律是否会被彻底抛弃？还是说，**信噪比问题**（喂进去的 99% 是无关内容）会永远存在，让上下文工程从「省钱技巧」演变为「质量保障」？你怎么看？
