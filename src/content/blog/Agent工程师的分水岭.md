*   **[概念类]**
    *   Harness Engineering：把不确定的模型装进一套确定、可靠、可控、可恢复、可审计的系统里的工程能力
    *   Agent 能力阶梯：从 Prompt Engineering 到 Business Engineering 的六级能力分层
    *   幂等性（Idempotency）：同一请求重复执行，系统状态不受影响的性质
*   **[技术类]**
    *   工具调用五层排查链路：Schema 设计 → 上下文缺失 → Prompt 约束 → 权限状态 → 编排返回值
    *   RAG 权限过滤：检索前过滤（Pre-filter）与检索后过滤（Post-filter）的取舍
    *   错误分类与退避重试：可重试/不可重试错误分类表，指数退避 + 抖动公式
    *   幂等三层落地：请求层 Idempotency Key → 工具层唯一索引/Upsert → Agent Loop 防重复检测
    *   Checkpoint 与状态机：任务状态表 + 每步落盘，故障后从最后 Checkpoint 恢复
    *   Context 分层压缩：System Prompt 固定，最近几轮保留原文，更早历史摘要化
    *   模型路由：任务分类打标签，小/中/强三档模型 + 置信度降级回退
    *   Trace 审计：trace_id + span_id + parent_span_id 还原完整调用树
*   **[应用类]**
    *   会议 Agent 四层系统设计：事件层 → 编排层 → 工具层 → 可靠性层
    *   ROI 四组量化指标：效率质量、采纳度、成本、净收益
    *   简历写法：用幂等、权限过滤、Checkpoint 等具体实现代替「接入大模型」

## 引言

前两年面试 AI 应用岗，考的是「你怎么优化 Prompt」。今天坐到面试官对面，问题完全是另一套：

> 如果 Agent 没权限访问这份文档，怎么办？工具调用超时，重不重试？重试之后订单被创建了两次怎么办？任务跑了 20 分钟，进程挂了，怎么接着跑下去？Context 爆了怎么处理？为什么这个任务非要用大模型，小模型不行吗？上线以后，你怎么证明它真的帮公司省钱了？

这是一位做了两年 AI 应用、准备跳槽的朋友的真实遭遇。他把 Prompt、RAG、Function Calling、LangChain、LangGraph、MCP 都过了一遍，结果面试题全是后端架构题。这大概率不是他一个人的遭遇，而是 **Agent 岗位面试正在发生的集体变化**：以前考「你会不会用大模型」，现在考「你能不能把大模型变成一套真正能在生产环境里跑起来的系统」。

这两件事之间的差距，比大多数人想象的要大得多。本文把这场面试背后的每一项工程能力拆到可以落地写代码的颗粒度。

## 一、从「会用」到「能做完」：范式转变

最早做 AI 应用，链路很简单：Prompt 进去，模型出来答案。后来加上检索，变成 RAG；再后来有了 Tool Calling，模型可以调用工具、拿到结果、再继续推理——一个像模像样的 Agent Demo 就出来了。

问题是，一旦真让它替公司干活，事情就全变了。以「会议结束后自动生成纪要、提取待办、找到负责人、创建任务、发通知、存档」为例，每一步背后都藏着一个真实问题：

- 这个员工有没有权限读这份纪要？
- 创建任务的请求被重复调用，会不会生成两条一样的任务？
- 通知发出去了但响应包丢在半路，算成功还是失败？
- 模型接口返回 429 该怎么处理？
- 跑到第四步进程死了，怎么接着跑？
- 会议内容太长，模型窗口装不下怎么办？
- 出了问题，谁能证明是谁授权、谁执行的？

> Agent 真正的难点早就不是让模型给出答案，而是让模型在一个混乱、有权限约束、随时可能出错的真实环境里，把事情从头到尾做完。

这也是为什么 OpenAI 在自己的 Agent 工程指南里，把 Model、Tools、Instructions、Orchestration、Guardrails 并列为基础设计要素，而不是把 Agent 简单等同于「调一次模型」。

## 二、疑难点深度解析一：工具调用排查的五层链路

**所需基础知识：**

> 在深入本节之前，建议你先了解：Tool Calling（函数调用）的基本机制——模型输出结构化调用请求，由编排层执行并返回结果；以及 Tool Schema 的字段语义（name、description、parameters、required）。

**概念详解：**

「模型经常不按要求调用工具，你怎么排查？」答这道题不能只说「改 Prompt」，要按一条完整的排查链路走下来，每一层都有具体动作。

**第一层：看 Tool Schema 本身。** 很多时候模型不调用工具，不是不想调，而是判断不出该不该调。检查 description 是否只写了工具名没写使用场景：

```
❌ "搜索订单"
✅ "当用户询问某个具体订单的状态、金额或物流信息时调用，需要提供 order_id 或客户手机号"
```

同时检查参数是否标了 `required`，可选参数是否有默认值和示例值——模型对「这个参数到底要不要填」，经常是靠 Schema 里的措辞猜的。

**第二层：看 Context 里有没有缺关键信息。** 比如工具需要 `user_id`，但对话历史里从未出现过，模型编不出来，自然不触发调用。正确做法是在 System Prompt 或第一轮消息里显式注入这些「环境变量」，而不是指望模型推断。

**第三层：看 Prompt 约束是否明确。** 想要「只要用户问到具体数值就必须调用工具查证，不能凭记忆回答」，就要在 System Prompt 里写硬约束：

```
对于任何涉及具体金额、日期、状态的问题，禁止依赖已有知识回答，必须调用对应工具核实。
```

**第四层：看权限和状态。** 工具调用请求有没有被网关拦截、Session 有没有足够权限 Scope、业务状态机是否压根不允许当前阶段调用——这些是工程问题，和 Prompt 无关，但外在表现都是「模型不调用工具」。

**第五层：看编排层有没有正确处理返回值。** 有些框架里模型已正确发出 Tool Call，但 Orchestrator 解析 JSON 失败，或把 Tool Result 塞回上下文的格式不对，导致模型下一轮「以为」调用失败而放弃。这一步通常靠打日志、把每轮原始 Request/Response 落盘来定位。

**示例：**

把五层链路实现为一个排查函数，每一层输出对应的检查动作：

```python
def diagnose_tool_not_called(model_output, tool_defs, session, trace_logs):
    """
    排查"模型不调用工具"问题，按五层链路逐层检查。
    返回每层的问题列表（命中即嫌疑点）。
    """
    issues = []

    # 第一层：Tool Schema 质量
    for tool in tool_defs:
        desc = tool["description"]
        if len(desc) < 20 or "调用" not in desc:  # description 过于简短
            issues.append(f"L1 Schema: {tool['name']} 的描述缺少使用场景")

    # 第二层：上下文关键信息缺失
    required_params = {p for t in tool_defs for p in t.get("required", [])}
    session_keys = set(session.get("env_vars", []))  # 会话中已注入的环境变量
    missing = required_params - session_keys
    if missing:
        issues.append(f"L2 Context: 上下文缺少 {missing}，模型无法构造调用参数")

    # 第三层：Prompt 硬约束
    if "必须调用" not in session["system_prompt"]:
        issues.append("L3 Prompt: 缺少'具体数值必须调用工具核实'的硬约束")

    # 第四层：权限与状态机
    if not session.get("has_permission"):
        issues.append("L4 Auth: 网关/会话未携带足够权限 Scope")

    # 第五层：编排层返回值解析
    for log in trace_logs:  # 检查 Tool Result 是否被正确解析回填
        if log.get("tool_result_parse_failed"):
            issues.append(f"L5 Orchestrator: 第 {log['round']} 轮 Tool Result 解析失败")

    return issues if issues else ["未发现异常，需结合完整 Trace 进一步定位"]
```

> 面试时把这五层讲清楚，比单纯说「我会调 Prompt」有说服力得多。

## 三、疑难点深度解析二：重试、幂等与 Checkpoint

本节是 Agent 生产化最核心的三块地基。我们逐层拆解。

### 3.1 错误分类与退避重试

**所需基础知识：**

> 在深入本节之前，建议你先了解 HTTP 状态码语义：429 限流、5xx 服务端临时异常、4xx 客户端错误；以及指数退避（Exponential Backoff）与抖动（Jitter）的基本思想。

**概念详解：**

面试官问「模型调用返回 503，怎么办」，初级答案是「重试」；追问「所有错误都重试吗」，差距就出来了。回答里直接给出错误分类表：

| 可以重试 | 不该重试 |
| ---- | ---- |
| 429（限流） | 401（认证失败，重试也没权限） |
| 500/502/503/504（服务端临时异常） | 403（权限不足） |
| 网络超时、连接被重置 | 404（资源不存在） |
| | 400（请求参数本身有问题） |

退避策略上，指数退避 + 抖动是标准做法：

```text
delay = min(base_delay * (2 ** attempt), max_delay)
delay_with_jitter = random(0, delay)
```

例如 base_delay = 500ms、max_delay = 30s：第一次等待 0~1 秒，第二次 0~2 秒，第三次 0~4 秒，一路封顶到 30 秒。同时设总 Retry Budget（最多 5 次或总耗时不超过 2 分钟），超限升级人工。

**Jitter 是最容易漏掉的一环**：所有并发请求按相同固定间隔重试，会在某时间点集中打爆下游，形成「重试风暴」；随机化能把重试请求打散。

### 3.2 幂等性三层落地

**所需基础知识：**

> 在深入本节之前，建议你先了解：哈希函数与缓存（Redis）的用法；数据库唯一约束；以及 Agent Loop 的基本循环（观察—思考—行动）。

**概念详解：**

假设 Agent 调用「创建订单」，请求已到达服务端并成功，但返回结果时网络断了。Agent 没收到确认，以为失败又调用一次——一个订单变成两个。这就是幂等性问题，实现分三层：

**第一层，请求层幂等。** 生成 Idempotency Key，把用户 ID、工具名、动作类型、业务关键参数拼接后哈希：

```python
import hashlib

def build_idempotency_key(user_id: str, tool_name: str, action: str, business_params: dict) -> str:
    """
    请求层幂等：由业务参数唯一确定一次操作。
    同一份参数在窗口期内重复发起，只会真正执行一次。
    """
    canonical = ":".join(
        sorted(f"{k}={v}" for k, v in business_params.items())  # 参数排序，保证键的确定性
    )
    raw = f"{user_id}:{tool_name}:{action}:{canonical}"
    return hashlib.sha256(raw.encode()).hexdigest()
```

Key 在发起调用前先查 Redis：命中则直接返回之前存的结果，不再执行；未命中则在处理开始时写入 Key（TTL 5 分钟），处理完成后把结果也存入（TTL 延长到 24 小时）。这样短时间收到两次相同请求，第二次只是读缓存。

**第二层，工具本身的幂等设计。** 外层 Key 缓存不够，下游系统本身也要支持幂等：对「订单唯一标识」字段加数据库唯一索引，重复插入直接被拒绝；用 `INSERT ... ON CONFLICT DO UPDATE`（Upsert）代替普通 Insert；创建前先按业务主键查是否存在；或把创建动作设计成状态机驱动，只有当前状态允许转移时才执行写操作。

**第三层，Agent Loop 防重复检测。** 每次工具调用的「工具名 + 参数」归一化后取哈希，存入滑动窗口，连续 3 次哈希完全相同即判定循环，触发告警或中断。这是兜住前两层的最后一道保险。

### 3.3 Checkpoint 与状态机

**所需基础知识：**

> 在深入本节之前，建议你先了解：状态机的状态转移概念；以及 Durable Execution（如 Azure Durable Functions）把工作流状态持久化、支持从故障点恢复的思想。

**概念详解：**

一个 Agent 要走 20 步，跑到第 15 步服务器重启。没做 Checkpoint 的 Agent 会从第一步重来——Token 重新算一遍，工具重新调一遍，已完成的业务操作也可能被重复触发。

具体实现是为每个任务维护一张状态表，每完成一个关键步骤就写一行：

| 字段 | 说明 |
| ---- | ---- |
| task_id | 任务唯一标识 |
| step_index | 步骤序号 |
| step_name | 步骤名 |
| status | pending / running / completed / failed |
| input_snapshot | 步骤输入快照 |
| output_snapshot | 步骤输出快照 |
| updated_at | 更新时间 |

任务状态机：`queued → running → completed`；出错走 `running → failed → retry → running`；需人工确认走 `running → paused → waiting_approval → running`。

**关键的实现细节是：每完成一步就同步落盘，而不是等整个任务结束才写一次。**

进程重启后的恢复逻辑：扫描状态表里所有 `status = running` 但心跳超时的任务 → 读出最后一条 completed 的 Checkpoint → 把 `output_snapshot` 重新加载成当前上下文 → 跳过已完成步骤，从下一步继续。

> 理解了这一点，你会发现 Agent Runtime 本质上就是一个 Durable Workflow Engine，只是执行的步骤里有一步是「调用 LLM」。

## 四、RAG 权限过滤与 Context 分层压缩

### 4.1 权限怎么真正进检索管道

**所需基础知识：**

> 在深入本节之前，建议你先了解 RAG 基本流程（切块 → Embedding → 向量检索 → 拼接 → 生成）以及向量数据库的 Metadata Filter 功能。

**概念详解：**

企业场景里最扎心的问题：员工让 Agent 总结一份内部文档，你怎么保证他看不到自己没权限看的内容？两种主流做法：

**方案一：检索前过滤（Pre-filter）。** 给每个 Chunk 的 Metadata 打上 `acl` 字段（有权限访问的部门 ID 或角色列表），检索时把用户权限集合作为过滤条件传给向量库：

```sql
-- Milvus / Elasticsearch 风格的过滤表达式
acl IN (user.department_ids) OR acl = 'public'
```

数据库在检索阶段就排除没权限的内容，而不是先查出来再判断。优点是效率高、检索结果干净；缺点是权限变更后需要重新打标签或增量同步。

**方案二：检索后过滤（Post-filter）。** 先按语义相关性查 Top-K，再逐条查权限系统过滤，剩下的才送进模型。缺点是如果 Top-K 前几条恰好全被过滤，剩余内容语义相关性可能很低。工程上通常把 Top-K 设得比实际需要大（如需要 5 条先查 20 条），留出被过滤的余量。

> 「检索到了相关内容」和「这个人有权限看这些内容」，永远是两件事。

不管哪种方案，链路上必须是：**身份识别 → Authorization → Retrieval → 拼接 Context → 送进 LLM**。Agent 不能因为用的是后台服务账号，就默认拥有比当前用户更大的权限——这一点要单独写进架构图，用显式的 Authorization 节点表示。OpenAI 也特别提醒：Guardrails 不能替代认证和授权。

### 4.2 Context 爆了怎么办

Agent 跑得越久，上下文越容易变成灾难。实用做法是分层管理，给上下文窗口划预算（以 128K 窗口为例）：

- **System Prompt 和工具定义**：占固定几千 Token。
- **最近 5 轮完整对话**：保留原文。
- **5 轮之前的历史**：做摘要压缩。
- **工具返回的大段原始数据**：只保留摘要和引用 ID，需要细节时按 ID 重新检索。

压缩的具体做法：每隔几轮，用一个较小、较便宜的模型把已过去的对话历史压缩成结构化摘要，保留关键事实、已做出的决策、还没解决的问题，丢掉过程性探索细节：

```
原始："模型先搜了 A，发现不对，又搜了 B，又搜了 C，最后确认是 D"
压缩后："已确认目标为 D"
```

大文件（几万字文档）只在上下文放摘要加可检索引用，模型需要原文细节时再触发针对性检索，而不是一开始就塞全文。

## 五、模型路由、可观测性与 ROI

### 5.1 为什么不能永远用最强的模型

假设每天一百万次 Agent 调用，每次都最贵最强的模型，财务部门很快就会找你。路由实现通常是：先用轻量分类器（规则或小模型）对任务打标签，再按标签选模型。分类维度包括任务类型、输入长度、是否多步推理、历史人工修改率。

| 任务类型 | 模型档位 | 成本 |
| ---- | ---- | ---- |
| 摘要、分类、格式转换、简单信息提取 | 小模型（低延迟） | 旗舰的约 1/10 |
| 普通文档分析、常规代码修改、中等问答 | 中间档 | 中等 |
| 复杂推理、长文档综合理解、复杂代码生成 | 旗舰模型 | 最高 |

同时留 Fallback 机制：小模型输出置信度低或触发质量校验规则（格式不对、关键字段缺失）时，自动升级到强模型重跑。并记录每次调用的模型档位、Token、延迟、人工修改率，定期回看调整分类器阈值——路由策略要持续迭代。

### 5.2 Trace 到底记什么

如果 Agent 能查客户资料、改 CRM、创建订单、发邮件，企业一定会问：刚才是谁让它这么干的？参考 OpenTelemetry 的思路：

- 每个任务一个 **trace_id**。
- 任务里每一步（一次模型调用、一次工具调用）一个 **span_id**，记录 **parent_span_id** 表示触发来源，并行分支也能还原完整调用树。
- 每个 Span 至少记录：触发者身份（用户/服务账号）、调用的工具和入参、返回结果或报错、开始/结束时间戳、Token 消耗和成本。

数据要支持两类查询：按 trace_id 查某次任务的完整执行过程（调试复盘）；按用户或工具聚合（「过去一周谁改了 CRM、改了哪些记录」，支撑审计和异常检测）。OpenAI Agent SDK 已把 Tracing 做成基础能力——可观测性是 Agent 运行时该有的基础设施，应从第一天接入，而不是出事后再补。

### 5.3 Agent 的 ROI 怎么算

「上线以后效果很好」没有说服力，真正拿得出手的是量化指标：

- **效率 + 质量**：人工 30 分钟 vs Agent 3 分钟，换算人力小时节省。但还要看准确率、完成率、人工修改率——如果 Agent 3 分钟生成纪要，员工要花 25 分钟重改，真实效率要按「人工总耗时」重新算。
- **采纳度**：日活、周活、留存、调用次数、重复使用率。一个号称覆盖十万员工的 Agent，如果每周只有 300 人用，采纳率不到 1%，只是做得比较漂亮的 Demo。

```text
ROI = (节省的人力成本 - 模型调用成本 - 工具/MCP调用成本
       - 基础设施成本 - 开发维护成本) / 总投入成本

节省的人力成本 = 人工处理耗时 × 涉及人数 × 单位时间人力成本
模型调用成本   = 实际 Token 消耗 × 对应模型单价
```

如果这两项算不出来，说明监控和统计层还没搭起来，这也是需要在方案里提前说明白的一部分。

## 六、现场系统设计：会议 Agent 的四层架构

**所需基础知识：**

> 在深入本节之前，建议你先了解事件驱动架构（Webhook）、消息队列、以及「状态表 + Checkpoint」的持久化模式。

**概念详解：**

面试官出题：设计一个会议结束后自动生成纪要、提取待办、分配负责人并通知相关人员的企业 Agent。完整设计分四层：

**① 事件层。** 由会议系统 Webhook 触发任务。Webhook 必须带业务唯一 ID（会议 ID），用于生成后续 Idempotency Key，防止会议系统偶发重复推送导致同一场会议被处理两次。

**② 编排层。** 负责状态机、上下文管理、工具路由、重试和 Checkpoint。实现上是一个轻量任务队列 + 状态表，每个任务对应一行记录。核心是：执行前先查状态，执行后立刻落盘。

**③ 工具层。** 会议 API（读纪要）、文档 API（存档）、通讯录 API（查负责人）、任务系统 API（创建待办）、IM API（发通知）、云盘 API。通过 MCP 或类似协议统一接入，每个工具的 Schema 都要写清使用场景和参数说明。

**④ 可靠性层。** 存状态的数据库、Checkpoint 表、失败重试的消息队列、幂等 Key 缓存、审计日志存储、监控告警——这是前三层稳定跑起来的地基。

**整条链路：**

```text
Webhook 触发 → 编排器接手(生成 Idempotency Key)
→ 读取纪要(权限校验) → 模型提取待办 → 查负责人
→ 创建任务(幂等写入) → 发通知(失败进重试队列)
→ 生成总结存云盘 → 全程写 Trace → 进 Dashboard
```

**面试官追问细节的答案：**

- Webhook 重复发送 → 会议 ID 生成的 Idempotency Key 在编排层拦掉。
- 创建任务超时 → 错误分类 + 退避重试，任务创建接口在数据库层加唯一索引兜底。
- 服务器中途挂掉 → 状态表 Checkpoint 恢复，从下一个未完成步骤继续。
- 员工没权限 → 读取纪要时做 Authorization 校验，检索前过滤。
- 会议太长 → 纪要摘要走分层压缩，只把结构化关键信息喂给提取待办的那次调用。
- 模型太贵 → 简单信息提取用小模型，复杂语义理解用中等模型。
- 出问题复盘 → 用 Trace 里的 trace_id 串起整条链路。

## 七、小结：Agent 工程师的能力阶梯

把前面这些能力拉成一条线，大致是这样一层层往上走的：

1. **Prompt Engineering**：让模型按要求做事。
2. **RAG 和 Context Engineering**：给模型看什么信息、怎么权限过滤和压缩。
3. **Tool Calling**：让模型碰到外部系统，设计好 Schema。
4. **Agent Loop 和 Orchestration**：串行/并行判断、熔断参数。
5. **Harness Engineering**：权限校验、错误分类与退避重试、幂等 Key、状态机和 Checkpoint、Context 分层压缩、Trace/Audit、模型路由。
6. **Business Engineering**：回答「这个 Agent 到底创造了多少价值」，用效率、质量、采纳度和 ROI 数据说话。

普通 AI 应用关心模型能不能回答；Agent 应用关心模型能不能行动；生产级 Agent 要多想行动安不安全、失败了能不能恢复、任务能不能几天后接着跑完、到底给企业创造了多少价值——而且答案都要落到具体的参数、公式和代码结构上。

> 接入大模型，只能证明你会用 AI；把 Agent 做成一套真正可靠的生产系统，才算真正懂 Agent。

### 延伸思考与创意展望

基于以上讨论，我们可以进一步思考以下方向：

1.  **Harness 的「可测试性」标准化**：本文讨论了幂等、重试、Checkpoint 的实现细节，但 Agent 的 Harness 目前缺少一套类似传统软件「单元测试」的标准验证框架。未来可能出现「故障注入测试套件」——像混沌工程注入网络分区那样，自动对 Agent 注入权限缺失、超时、重复调用、进程崩溃等故障，验证 Harness 是否真的兜得住。Agent 的可靠性将被「量化证明」，而非「口头承诺」。

2.  **审计从「记录」走向「策略」**：现在的 Trace 主要是事后审计（发生了什么）。下一步是让 Trace 反向驱动实时策略——根据调用模式自动发现异常（如某服务账号突然高频调用写操作、某个 Agent 正在尝试访问超出职责范围的数据），在造成损失前自动熔断或升级人工审批。可观测性将从「日志」进化为「实时治理」。

3.  **开放性问题：当 Harness 本身也由 Agent 自动生成时，「Agent 工程师」的上限在哪里？** 本文描述的能力阶梯第六层是 Business Engineering（证明 ROI）。如果未来 AI 能自动完成幂等设计、Checkpoint、Trace 接入，工程师的核心价值是否会进一步上移到「定义什么是值得做的 Agent」和「定义如何度量价值」？到那时，Agent 工程师和产品经理的边界会不会消失？你怎么看？
