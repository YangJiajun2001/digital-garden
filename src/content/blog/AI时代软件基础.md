## 引言

2026 年，AI 编程席卷一切。TypeScript 教育者 Matt Pocock 站上 AI Engineer Summit 的舞台，在 18 分钟的闪电演讲中说出了一句全场开发者都想听的话：**你的技能没过时，软件基础比以往任何时候都重要。**

他不是来推销 AI 工具的。他搬出了四位经典软件工程作者——John Ousterhout、Fred Brooks、Kent Beck、Eric Evans——并断言：这些名字在 AI 时代不但没过时，反而成了你手中**最硬的通货**。

本文将拆解这场演讲的核心逻辑：AI 编码为什么会越写越烂、经典理论如何解释这些现象，以及那五个可落地的实战技巧究竟该如何使用。

---

## 一、Spec-to-Code 的陷阱：每次循环，代码更烂

Matt 开场就描述了一个在场大多数人都经历过的场景。有一种被称为 **Spec-to-Code** 的 AI 编码模式：你写一份需求规格说明，AI 生成代码；出了 bug？不碰代码，回去改 spec 再重新生成。

听起来很美好。Matt 试了，结果令人沮丧：

> 第一次跑：拿到代码。第二次跑：更烂的代码。第三次跑：更更烂的代码。一直跑到最后，垃圾。

他引用《程序员修炼之道》解释这一现象——**软件熵（Software Entropy）**。每次你只盯局部改动，不思考系统整体设计，代码库就往崩溃的方向滑一步。**AI 把这个过程加速了。**

Spec-to-Code 的支持者主张"代码很廉价"（code is cheap）。Matt 直言不买账：

> 烂代码是史上最贵的代码。代码库不可改，你就接不住 AI 能给你的生产力红利。

> 一句话理解软件熵：就像没有持续打扫的房间——杂物会越堆越多，而"顺手把东西放回原处"的努力一旦中断，凌乱就会自动加速。

---

## 二、把 AI 编码失败映射回经典理论

Matt 没有和 AI 工具的 hype 对轰，而是翻出经典著作，把常见的 AI 编码问题一条条映射回去。这张映射表，是整场演讲最"高级"的部分——观众对 AI 编码缺乏成熟的评判框架，但对这些经典著作有信任。一旦你说出"AI 的问题，其实就是 Ousterhout 说的复杂度问题"，一切瞬间就通了。

| 你遇到的问题 | 哪本书早就讲过 |
|------|------|
| AI 不听你的，做出来完全不对 | Frederick Brooks，《设计的设计》：「设计概念」 |
| AI 啰嗦得要死，沟通效率极低 | Eric Evans，《领域驱动设计》：「统一语言」 |
| AI 一次写太多，跑不起来 | 《程序员修炼之道》：「跑得比大灯快」 |
| 代码越改越难改 | John Ousterhout，《软件设计的哲学》：「复杂度」定义 |

这套映射说明一个残酷的事实：**AI 放大的是你原本就存在的软件基础问题，而不是制造了全新的问题。**

## 三、疑难点深度解析：五个实战技巧

Matt 给了 5 个可实操的 skill（开源在 MattPocockSkills 仓库）。它们不是并列的清单，而是一层层往下走的：**先达成共识 → 统一语言 → 小步迭代 → 模块化 → 委派实现。**

### 技巧一：Grill Me（拷问我）——写代码前先达成共同设计概念

**所需基础知识：**

> 在深入本节之前，建议你先了解 Frederick Brooks 的**设计概念（Design Concept）**：多人协作设计时，存在一个无形的、飘在参与者之间的"共同理解"，它无法写进文档，一旦丢失，整个设计就会散架。

**概念详解：**

Grill Me 的核心是一句极具杀伤力的指令，让 AI 在写任何代码之前，先反问你 40 到 100 个问题：

> "Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one by one."
> （无情地盘问我这个计划的每一个方面，直到我们达成共识。沿着设计树的每个分支走，逐一解决决策之间的依赖关系。）

它的作用不是帮 AI 写代码，而是**帮你把需求想清楚**。Matt 直言，这比 Claude Code 自带的 plan mode 好用——"plan mode 太急于产出资产了，它只想赶紧搞个计划然后开干"，而不是先达成共同设计概念。

**示例：**

```markdown
<!-- Grill Me skill 的核心提示词（可放入 CLAUDE.md 或项目文档） -->
<role>
你是本项目的设计评审官。在开始写任何代码前，你必须先与我完成一轮设计访谈。
</role>

<rules>
1. 逐条盘问我对计划的每一个假设，直到我们达成共识
2. 沿着设计树的每个分支走，逐一解决决策之间的依赖关系
3. 当我给出含糊的答案时，继续追问，禁止自行脑补
4. 达成全部共识后，汇总成一份设计决策清单，再开始编码
</rules>

<goal>
先建立"共同设计概念"，再动手写代码，避免 Spec-to-Code 式的盲目生成。
</goal>
```

### 技巧二：统一语言（Ubiquitous Language）——消灭沟通噪音

**所需基础知识：**

> 在深入本节之前，建议你先了解 DDD（领域驱动设计）中的**统一语言（Ubiquitous Language）**：开发者和领域专家围绕业务领域，建立一套完全一致的术语体系，避免"同一个东西各有各的叫法"导致的沟通损耗。

**概念详解：**

你觉得 AI 特别啰嗦？Matt 说，根因是**你们没有共享术语**。AI 每次对话都要重新猜测你的术语含义，自然就产生了大量试探性的废话。

他的解法是写一个 skill：扫描你的代码库，自动生成一份**术语表 Markdown 文件**，并在所有 AI 对话中引用它。效果立竿见影——Matt 原话："读 AI 的思维轨迹时发现，不光是规划更好了，AI 的思考也更精简了。"

**示例：**

```markdown
<!-- 统一语言 skill 生成的术语表（glossary.md）示例 -->
# 项目术语表

| 术语 | 定义 | 代码中的体现 |
|------|------|--------------|
| 订单(Order) | 用户确认购买后的交易记录，状态机含 pending/paid/shipped | `Order` 接口、`orders` 表 |
| 结算(Settlement) | 订单支付成功后与支付渠道的对账过程 | `SettlementService` |
| 优惠券(Coupon) | 可抵扣订单金额的凭证，有有效期与使用条件 | `Coupon` 实体、`coupon_rules` 表 |

<!-- 所有 AI 对话开场自动附加：请严格遵循 glossary.md 中的术语定义，不要自行发明同义词。 -->
```

### 技巧三：TDD——用反馈循环对抗"跑得比大灯快"

**所需基础知识：**

> 在深入本节之前，建议你先了解两条前置知识：一是《程序员修炼之道》中"**跑得比大灯快**（outrunning your headlights）"的比喻——夜里开车，灯照到多远，你才能开多快；**反馈速度就是你的限速**。二是 TDD 的红绿循环：先写失败测试（红）→ 让测试通过（绿）→ 重构。

**概念详解：**

AI 的默认行为是一次性生成巨量代码，然后才想起去做类型检查——这就是典型的"跑得比大灯快"。TDD 是解药：**先写测试，让测试通过，再重构，强迫 AI 走小步。**

Matt 特别强调一个正反馈循环：

> 好代码库 = 容易测试的代码库。代码库越好，反馈循环越好。反馈越好，AI 产出的代码越好。

起点，是代码库质量。

**示例：**

```typescript
// 步骤 1：先写测试（红）——定义"购物车结算"的行为契约
import { describe, it, expect } from "vitest";
import { checkout } from "./checkout";

describe("checkout 结算逻辑", () => {
  it("空购物车不允许结算", () => {
    expect(() => checkout([])).toThrow("购物车为空");
  });

  it("结算后总价 = 商品单价 × 数量之和", () => {
    // 接口契约：传商品列表，返回总价
    expect(checkout([{ price: 20, qty: 3 }])).toBe(60);
  });
});

// 步骤 2：让 AI 实现使测试通过（绿）——实现被"测试边界"约束
export function checkout(items: { price: number; qty: number }[]): number {
  if (items.length === 0) throw new Error("购物车为空");
  // 小步实现，仅满足当前测试，禁止一次性堆砌大段逻辑
  return items.reduce((total, item) => total + item.price * item.qty, 0);
}
```

> 这套"先契约后实现"的写法，把 AI 从"自由发挥"约束为"按测试履约"——反馈距离短，错误无处遁形。

### 技巧四：深层模块 > 浅层模块——让 AI 看得懂你的代码

**所需基础知识：**

> 在深入本节之前，建议你先了解 John Ousterhout 在《软件设计的哲学》中对**复杂度**的定义，以及两类模块的划分（见下）。

**概念详解：**

回到 Ousterhout 的分类：

- **Deep Module（深层模块）**：大量功能藏在简洁接口后面。想看内部可以看，但不需要看，直接用接口即可。
- **Shallow Module（浅层模块）**：功能没多少，接口却很复杂。

Matt 的观察是：**AI 天然擅长创建浅模块密集的代码库**——一大堆零散的小函数、小文件。这种代码库对 AI 自己反而是灾难：它探索代码时会被碎片海淹没，"AI 搞不懂你的代码在做什么"。解法是持续重构：扫描代码库，把相关代码封装成深层模块。

**示例：**

```typescript
// 反面教材：浅模块——一个操作被拆成 N 个脆弱的小函数，调用方必须懂全部细节
export function validateEmail(v: string) { return v.includes("@"); }
export function validatePhone(v: string) { return /^\d{11}$/.test(v); }
export function formatAmount(n: number) { return `¥${n.toFixed(2)}`; }
// 调用方需要逐个 import 并自己组合这些零散校验，接口碎片化

// 正面示例：深层模块——把复杂逻辑收进简洁接口，调用方一行搞定
export class CheckoutService {
  // 隐藏了校验、算价、库存扣减、优惠计算等全部细节
  checkout(cart: Cart, user: User): OrderReceipt {
    // ...大量内部逻辑，调用方无需关心
    return receipt; // 对外只暴露极简的结果
  }
}
```

### 技巧五：设计接口，委托实现——人在战略层，AI 在战术层

**概念详解：**

五个技巧的终极形态，是一种清晰的人机分工：

1. **你设计模块边界和接口**——这需要软件基础
2. **AI 实现接口内部的细节**——被测试边界约束
3. **你在接口处写测试验证 AI 的产出**

Matt 原话："我直接说，AI，大块里面的东西交给你。我只需从外面测试验证。这真的拯救了我的大脑。"这就是 Kent Beck 那句"Invest in the design of the system every day"（每天投资于系统的设计）的最佳注脚。

## 四、两种范式：Spec-to-Code 与软件基础驱动

Matt 用军事类比收尾：**AI 是非常优秀的一线程序员**——战术层面，在战壕里改代码的士官。**但你需要有人在战略层面思考，那个人是你**，而这需要我们已经用了 20 年甚至更久的软件基础技能。

| Spec-to-Code | 软件基础驱动 |
|------|------|
| 写 spec → AI 生成 → 改 spec → 再生成 | Grill Me 共识 → 统一语言 → TDD → Deep Module |
| 不看代码 | 设计接口，AI 填实现 |
| 代码质量持续下降 | 代码质量持续改善 |
| 人越来越被动 | 人越来越像将军 |

**Spec-to-Code 是在撤资；你在做的，才是投资。**

## 五、必读经典：四本书 + Kent Beck

Matt 整场演讲引用了四本经典，外加 Kent Beck。如果只读其中一本，**从 Ousterhout 开始**。

### 《软件设计的哲学》（A Philosophy of Software Design）

John Ousterhout 著。薄薄一本不到 200 页，但每一章都在直击要害。Ousterhout 是斯坦福教授，整本书只讲一件事：**复杂度从哪来，怎么消灭它**。"深层模块"这个概念就是这本书提出的。如果你写代码超过两年，这本书会让你重新审视每一个 `export`。

### 《程序员修炼之道》（The Pragmatic Programmer）

Andy Hunt & Dave Thomas 著。软件工程界最接近"圣经"的东西，1999 年首版，20 周年出了几乎全部重写的第二版。"破窗理论""软件熵""跑得比大灯快""石头汤"——无数经典隐喻出自此书。不用从头读到尾，随便翻开一章都能学到东西。

### 《设计的设计》（The Design of Design）

Frederick P. Brooks 著。《人月神话》作者的晚年设计反思。"设计概念"是主要论点，也是 Grill Me 技巧的理论基础。

### 《领域驱动设计》（Domain-Driven Design）

Eric Evans 著。2003 年的"大蓝书"，在 AI 时代突然翻红不是偶然——它逼你建立开发者与领域专家共用的术语体系，这恰好是与 LLM 高效协作的必需品。Matt 说"读到每一页都像在听音乐"。书很厚，建议先读 Part II（模型驱动设计的构建块）和 Part III（重构加深理解）。

### 题外话：Kent Beck

TDD 和极限编程（XP）之父、敏捷宣言签署人。他写了两本你应该知道的书：《测试驱动开发》（*Test-Driven Development: By Example*）——TDD 的开山之作；《解析极限编程》（*Extreme Programming Explained*）——XP 的精髓。Matt 的第三个技巧，底层就是 Beck 的方法论。

## 小结

Matt Pocock 这场演讲为什么"炸"？因为他道出了一个反直觉的真相：

> **AI 编程工具越好用，好代码库和烂代码库之间的差距就越大。**

- **好代码库里，AI 如虎添翼。**
- **烂代码库里，AI 加速腐烂。**

你的软件基础技能——模块设计、接口定义、测试策略、领域建模——以前值钱，现在更值钱。它们决定了你能从 AI 那里撬出多少生产力。

### 延伸思考与创意展望

基于以上讨论，我们可以进一步思考以下方向：

1.  **设计评审的自动化闭环**：Grill Me 目前是"单向拷问"，未来完全可以演化为"设计评审双循环"——AI 拷问你的同时，也把你的回答沉淀成一份可版本化的设计决策库（ADR），每次需求变更自动 diff 决策库，反向提醒你"哪些隐含假设已经失效"。设计概念从"飘在空中的默契"变成"可审计的资产"。

2.  **统一语言的"活体化"演进**：术语表目前是扫描代码库生成的静态文件。随着 AI 生成更多代码，它应当反向成为代码的"宪法"——通过 lint 规则和类型系统强制术语一致性，例如用 TypeScript 的类型别名把领域术语"钉"进类型层，让类型错误直接暴露术语漂移。术语不再是文档，而是**可执行约束**。

3.  **开放问题**：当 AI 能够自己调用 Grill Me、自己写 TDD、自己重构出深层模块时，"战略层的人"这个角色还能存在多久？软件基础的稀缺性，究竟会因 AI 而放大，还是终将被 AI 内化？你更愿意押注哪一边？
