### 知识点总结与分类

*   **[概念类]**
    *   Agentic Development：智能体开发范式，指 Agent 能够自主规划、连续运行并完成复杂任务的开发方式
    *   Developer 与 Builder：二者边界逐渐模糊，Builder 被定义为「任何依靠 AI 完成自己工作的人」
    *   「旧流程加速」与「业务流程再造」：AI 的价值不应止步于让原有流程变快，而在于重新设计整个业务
*   **[技术类]**
    *   Evaluation Harness（评估机制）：通过一组明确的测试与标准，判断 Agent 是否真正完成了目标任务
    *   模型演进的时间轴思维：围绕模型三个月、六个月后的能力做设计，而非绑定今天的模型
    *   问题定义能力：目标不清晰时，Agent 运行得越久，偏离方向的风险越高
*   **[应用类]**
    *   出海本地化适配：监管政策、数据隐私、数据主权规则的本地化重新理解
    *   Agent Manager 能力：未来开发者需要同时管理多个 Agent，从技术执行转向任务协调、优先级排定与冲突消解
    *   照片整理 Agent 案例：从「想解决什么问题」出发，几小时构建分类、评估、筛选照片的 Agent 团队

## 引言

每周都有新模型发布，新工具刚学会就可能被替代——这几乎是每一个 AI 从业者共同的焦虑。我们到底应该学哪项技术？哪些能力才不会过时？

2026 年 Google 开发者大会期间，Datawhale 与 Google 全球开发者生态总监 **David McLaughlin** 进行了一场深度对谈，围绕中国开发者出海、Agentic Development 的下一步、AI 时代开发者能力的变化，以及一个越来越重要的问题：

> 当写代码的门槛不断降低，我们应该如何重新理解 Developer 和 Builder？

David 给出的答案很直接：

> 与其问「我应该学习什么技能」，不如先问「我到底想解决什么问题」。

这篇文章将完整梳理这场对谈的核心观点，并用工程化的视角，把「Agent 时代开发者需要哪些能力」这一问题拆解到可以落地实践的颗粒度。

## 一、Agent 的价值：不是让旧流程更快，而是重新设计业务

**所需基础知识：**

> 在深入本节之前，建议你先了解 Agent（智能体）的基本形态：LLM 通过工具调用、多步推理完成目标任务，并能较长时间自主运行。

**概念详解：**

David 认为，我们目前仍处于智能体开发非常早期的阶段。现阶段，很多企业正在尝试用 Agent 优化现有业务流程，比如：

> 「能不能让 Agent 一直处理这项工作，让流程变快？」
>
> 「能不能把原本需要几小时完成的任务，再缩短一些？」

但这只是最容易想到的一层。真正值得思考的问题是：

> 当 Agent 可以 24 小时持续工作时，哪些原有流程已经不再需要存在？
>
> 当 Agent 可以长时间自主运行时，我们能不能重新设计整个业务？

David 用了一个非常形象的比喻：开发者不应该只想着**造一辆跑得更快的马车**，而应该开始思考：**如果我们已经能够造汽车了，那意味着什么？**

| 思维层次 | 典型问题 | 本质 |
| ---- | ---- | ---- |
| 第一层：流程优化 | 能不能让 Agent 一直处理这项工作，让流程变快？ | 旧流程的自动化 |
| 第二层：流程再造 | 当 Agent 24 小时工作，哪些环节已经不需要存在？ | 对业务本身的重新设计 |

**示例：**

这个比喻可以落地为一个简单的思维模型。假设一家公司原有的订单处理流程是「人工确认 → 系统录入 → 人工审核 → 通知客户」：

```text
# 旧流程（以人为主）：
人工确认订单 → 系统录入 → 人工审核 → 通知客户     # 每一步都需要人

# 新流程（以 Agent 为主）：
Agent 自主确认订单 → Agent 自动录入并交叉核验
→ Agent 按规则审核（超阈值自动升级人工）
→ Agent 自动通知客户并归档                      # 人在其中只保留「异常兜底」
```

前者是「跑得更快的马车」——把人工换成 Agent，流程结构不变；后者是「汽车」——审核环节本身可能被规则引擎和自动核验取代，整个流程的拓扑结构都发生了改变。**AI 带来的机会，来自对产品、组织方式和商业模式的重新设计，而不仅仅是效率的提升。**

## 二、疑难点深度解析：工程思维为什么反而更重要

本节是全文的核心难点：AI 降低了编程门槛，但为什么基础的工程思维反而变得更重要了？

**所需基础知识：**

> 在深入本节之前，建议你先了解：Agent 的基本循环（观察—思考—行动）、工具调用的基本机制，以及「任务拆解」（Task Decomposition）和「结果评估」（Evaluation）的基本概念。

**由浅入深的理解路径：**

**第一步，先看历史类比。** 在过去，精通汇编语言是一项非常有价值的能力。但随着编译器和高级编程语言的出现，这种「记忆具体语法细节」的能力价值大幅下降——没有人会因为你背得出全部汇编指令而付你高薪。David 认为，AI Coding 时代正在重演这一过程：精确记住某种编程语言的语法，或熟练掌握某个特定 API 的所有细节，这类技能的价值会逐渐下降。

**第二步，识别「技能」与「思维」的差别。** 技能下降的只是**记忆类、操作类**的硬技能。与之相对的，**工程思维**——理解问题真正的需求、把复杂问题拆解成更小的任务、将不同任务分配给不同 Agent、判断各个环节是否达到了预期结果——这类能力恰恰相反，会变得更加重要。

**第三步，深入 Evaluation Harness 这一核心概念。** 当 Agent 可以自主运行十二小时、三天甚至一整周时，开发者面临的核心问题发生了变化：

> 我们有没有把问题定义清楚？
>
> 什么样的结果才算成功？
>
> 如何判断 Agent 是否真的完成了任务？

回答这些问题，需要一套 **Evaluation Harness（评估机制）**：通过一组明确的测试和标准，判断 Agent 是否真的完成了我们希望它完成的事情。David 明确表示，这不是一项简单的能力，它需要经验、判断力和大量思考——你必须能够清楚地说出：**这就是我们要解决的问题，这就是成功的标准。**

**示例：**

假设你要构建一个「自动整理会议纪要并提取待办」的 Agent，Evaluation Harness 可以这样设计：

```python
def evaluate_meeting_agent(agent, sample_meetings):
    """
    评估一个会议 Agent 是否真正完成了任务。
    harness 的三层结构：结果校验 → 副作用检查 → 成本与质量权衡。
    """
    passed = 0
    for meeting in sample_meetings:                      # 标准测试集
        result = agent.run(meeting)

        # 1. 结果校验：待办是否被正确提取
        expected_todos = meeting["expected_todos"]
        if not set(result.todos) >= set(expected_todos):
            continue                                     # 关键待办缺失，判失败

        # 2. 副作用检查：是否重复创建了任务、是否误发通知
        if result.duplicated_task_ids or result.unsent_notice:
            continue                                     # 产生脏副作用，判失败

        # 3. 成本与质量权衡：人工修改率是否低于阈值
        if result.human_edit_ratio > 0.2:
            continue                                     # 需要人工大量返工，不合格

        passed += 1

    return passed / len(sample_meetings)                 # 通过率作为上线门槛
```

注意这套机制**不是代码的单元测试，而是任务级的验收标准**。它回答的不是「这段代码有没有 Bug」，而是「Agent 有没有把这件事做对」。定义问题的能力、设定边界的判断力、评估结果的严谨性——这些才是 AI 时代开发者最稀缺的工程能力。

## 三、未来，每个开发者都可能成为一名 Manager

**所需基础知识：**

> 在深入本节之前，建议你先了解多 Agent 协作的基本形态：多个 Agent 并行处理不同子任务，通过共享状态或消息进行协调。

**概念详解：**

David 在本次对谈中提出了一个很有意思的判断：未来，每一位 Developer、每一位 Builder，都需要开始把自己看作一名 **Manager**。

过去，开发者习惯独自工作，或在一个小团队中与其他人协作。但在 Agent 时代，一个开发者可能同时管理多个 Agent：

> 六个 Agent 在处理一个问题；三个 Agent 在处理另一个问题；还有十个 Agent 在执行其他任务。

这时，开发者面对的问题会越来越像一个团队管理者面对的问题：

- Agent 之间能否顺畅沟通？它们是否记录了自己的工作进度？
- 它们的优先级是否正确？它们是否在重复工作，或者互相干扰？
- 当一个 Agent 失败时，谁来接手重试？

因此，未来的开发者不仅需要懂技术，也需要懂得如何协调、分工和管理一支 Agent 团队。过去很多开发者不需要具备这样的管理能力，但它可能成为下一阶段的重要竞争力。

**示例：**

把「管理 Agent 团队」与「管理人类团队」对照起来看，二者的底层能力几乎一一对应：

| 人类团队管理 | Agent 团队管理 | 具体动作 |
| ---- | ---- | ---- |
| 明确分工 | 任务拆解与分配 | 把大任务拆成子任务，分配给对应 Agent |
| 进度同步 | 状态可观测 | 让每个 Agent 记录工作日志与进度快照 |
| 冲突消解 | 依赖与优先级管理 | 识别 Agent 间的资源争抢与重复劳动 |
| 质量控制 | 结果评估 | 对每个 Agent 的输出跑 Evaluation Harness |
| 人才梯队 | 模型路由 | 简单任务派给小模型，复杂任务升级旗舰模型 |

**工程落地上，一套简单的多 Agent 协调器并不复杂：**

```python
class AgentManager:
    """开发者即 Manager：调度多个 Agent 并监控其运行状态。"""

    def __init__(self, registry):
        self.registry = registry          # Agent 注册表：名称 → 执行器

    def dispatch(self, task, skills):
        """把任务按能力匹配分发给对应 Agent，并跟踪进度。"""
        for skill in skills:
            agent = self.registry.get(skill)          # 按技能选择 Agent
            task.submit(agent)                        # 提交子任务
            agent.logger.start()                      # 记录工作日志，保证可观测

    def detect_conflicts(self, tasks):
        """检测是否有 Agent 在重复处理同一个子任务（重复劳动）。"""
        seen = {}
        for t in tasks:
            if t.canonical_key in seen:
                return Conflict(seen[t.canonical_key], t)   # 发现重复，及时消解
            seen[t.canonical_key] = t
        return None
```

> 当开发者开始像管理者一样思考「如何协调、分工、评估」而非「如何自己写」，他实际上已经完成了从 Developer 到 Agent Manager 的角色迁移。

## 四、当专业知识与 AI 结合，每个人都可以成为 Builder

**所需基础知识：**

> 在深入本节之前，建议你先了解：LLM 的自然语言交互能力，以及低代码 / 无代码工具的基本形态。

**概念详解：**

随着自然语言和 AI 工具的发展，越来越多没有计算机科学背景的人开始构建自己的 AI 应用。David 用电子表格的发展做了一个类比：

几十年前，一个人能够构建复杂系统、处理大量数据并进行复杂计算，会被认为是一名专家级程序员。但后来，很多类似的事情可以通过 Spreadsheet 完成——使用电子表格并不要求一个人必须是程序员。真正懂金融、会计、教育或政策的人，也可以借助工具解决自己领域里的问题。

今天，我们可能正处在一个相似的阶段。越来越多 Builder 不具备传统计算机科学背景，但他们对自己的领域有很深的理解。AI 和 Agentic 工具正在赋予他们构建应用、设计流程和处理数据的能力。

**David 对 Builder 的定义是：任何依靠 AI 完成自己工作的人，都可以被称为 Builder。**

从这个意义上说，未来几乎每个人都有可能成为 Builder：一个人可能为自己的生活构建工具，可能为一家非营利组织解决问题，也可能为自己的公司设计新的业务流程。未来，AI 工具可能会像今天的电子邮件和电子表格一样，成为日常工作的一部分。

**示例：**

一个不懂代码的财务分析师，可以用自然语言描述需求，让 Agent 帮她构建一个自动化报表流程：

```text
用户（自然语言）：
"帮我做一个 Agent：每天早上从数据库拉取前一天的销售数据，
按地区、品类汇总，并标注环比异常超过 10% 的条目，生成简报发到团队群。"

Agent 生成的执行流程（可视化描述）：
拉取数据（SQL 查询） → 清洗与聚合（数据管道）
→ 异常检测（阈值规则） → 生成简报（模板渲染） → 发送通知（IM 接口）
```

在这个过程中，财务分析师不需要写一行 SQL 或配置一条管道——**她的领域知识（哪些异常值得关注、按什么维度汇总）才是不可替代的部分**。这正是「专业知识 + AI」成为 Builder 的典型路径。

## 五、技术变化这么快，我们到底应该学什么

**所需基础知识：**

> 在深入本节之前，建议你先了解：模型能力的迭代趋势（上下文长度、自主运行时长、工具调用的可靠性），以及「围绕问题而非围绕工具构建」的学习方法论。

**概念详解：**

这是很多 AI 学习者最关心的问题：新模型和新产品几乎每周都在出现，我们到底应该深入哪项技术、学习哪种工具、选择哪个方向？

David 没有直接给出一个技术名称，而是把问题重新抛了回来：**有没有一个你真正想解决的问题？**

在他看来，AI 模型最重要的价值之一，是放大人类的速度、创造力和创新能力。但前提是，你必须先找到一个值得解决的问题。它可以来自你的生活，也可以来自你的工作：

- 有哪些问题一直困扰着你？
- 有哪些问题真正让你感兴趣？
- 借助 AI，我现在能不能用一种两年前、五年前做不到的方式解决它？

David 分享了一个自己的例子：他和妻子都很喜欢拍照，长期积累了几十万张照片。他一直想整理和筛选这些照片，但因为整个过程太麻烦，迟迟没有真正开始。现在，借助 AI Agent，他只用了几个小时，就构建了几个能够分类、评估和筛选照片的 Agent。

这个案例并不会改变世界，但它说明了一件事：**AI 的价值，可以从一个非常具体的问题开始。** 照片整理可以用 Agent 解决，商业问题和更多复杂问题，同样可以尝试用新的方式解决。

所以，David 建议大家重新思考自己的学习路径：

> 与其问「我应该学习什么技能」，不如问「我到底想解决什么问题」。

当你真正开始解决问题时，自然会学会实现目标所需要的技能。

**示例：**

把「围绕工具学习」和「围绕问题学习」两种路径对比，差异一目了然：

| 维度 | 围绕工具学习 | 围绕问题学习 |
| ---- | ---- | ---- |
| 出发点 | 这个框架很火，学一下 | 我有一堆照片要整理，怎么用 AI 搞定 |
| 驱动方式 | 被技术更新推着走 | 被真实需求拉着走 |
| 技能沉淀 | 工具一变，技能贬值 | 问题解决能力，跨工具复用 |
| 迭代方向 | 学最新最热的技术 | 深挖一个领域，成为该领域专家 |
| 适配变化 | 追不上模型发布节奏 | 无论模型怎么变，问题始终存在 |

**更进一步，David 还给出了一条具体的技术判断：不要只围绕模型今天的能力设计产品。** 一个已经非常明显的趋势是，Agent 能够自主运行的时间会越来越长——今天可能只能独立完成一个相对简单的任务；未来，它可能持续运行六小时、十二小时、三天，甚至一整周。今天你在产品里留了多少「人工接管」的接口、多少「任务失败重试」的兜底，决定了它能否接住三个月后的模型能力。

## 六、给年轻 AI 学习者的建议：尽可能多地去 Build

访谈的最后，我们请 David 给年轻学习者一条建议：未来十二个月，最值得做的一件事是什么？

他的回答是：**尽可能多地去 Build。**

抽象知识当然重要，阅读和学习也依然有价值。但只有当知识被用于解决一个真实问题时，它才会真正与现实发生连接。这个问题可以很小，也可以很大。重要的是，**先开始动手**。

选择一个自己真正想解决的问题，尝试使用 Agent 去完成它。在这个过程中，你会自然学会问题拆解、工具使用、结果评估、产品设计，以及更多原本不知道自己需要掌握的能力。

## 七、结语：从知识的旁观者，成为真正的 Builder

回望整场对谈，一条清晰的逻辑链浮现出来：

1. **Agent 的价值**不在于让旧流程变快，而在于重新设计业务——与其造跑得更快的马车，不如思考汽车意味着什么。
2. **工程思维反而更重要**——定义问题、拆解任务、评估结果，这些能力不会因为编程门槛降低而贬值。
3. **开发者将成为 Manager**——管理一支 Agent 团队，协调、分工、评估将成为核心竞争力。
4. **每个人都可能成为 Builder**——领域专业知识与 AI 结合，就能构建解决自己问题的应用。
5. **学什么取决于想解决什么**——问题定义能力，是技术迭代浪潮中唯一稳定的锚点。

正如 David 所言，技术发展的速度会比想象中快得多。一些原本被认为还要五到十年才能实现的能力，可能在未来一两年内就会出现。因此，真正值得思考的问题是：

> **我们今天应该如何设计工具、公司和流程，才能提前适应这样的未来？**

当 AI 工具逐渐成为像电子邮件和电子表格一样普遍的基础工具，「谁是开发者」或许不再是最重要的问题。真正重要的是：**你看到了什么问题？你愿意为它做些什么？**

在 AI 快速变化的时代，与其追赶每一个新模型，不如先找到一个值得长期解决的问题。然后，开始 Build。

### 延伸思考与创意展望

基于以上讨论，我们可以进一步思考以下方向：

1.  **「Agent Manager」会成为新的职业角色吗？** David 预言每个开发者都会成为 Agent 的管理者，这暗示了一种全新的职业分工：专门负责设计、编排和审计 Agent 团队的角色。未来可能出现「Agent 运维工程师」「Agent 绩效评估师」——就像今天的人力资源管理者一样，只不过他们管理的对象是一支永不疲倦的智能体队伍。思考：当「管理」的对象从人变成 Agent，管理理论本身是否需要被重写？

2.  **Evaluation Harness 的行业标准化。** 本文介绍了用三层结构（结果校验、副作用检查、成本权衡）评估 Agent 的方法，但目前每家公司的评估体系都是各自为战。未来很可能出现类似「测试套件」的行业级 Agent 评估基准——由行业协会或头部公司发布「Agent 能力认证」，就像今天的软件测试标准一样。到那时，「我的 Agent 通过了 XX 认证」会成为企业采购时的核心信任凭证。

3.  **开放性问题：当「Builder」的门槛趋近于零，竞争的胜负手会落在哪里？** David 认为未来每个人都能成为 Builder，那么当人人都能用 AI 构建工具时，一项工具的真正护城河是什么——是数据积累、是领域场景的深度理解，还是对「问题定义」的洞察力？如果构建本身不再稀缺，会不会出现像「产品经理」一样新的稀缺角色：定义什么是值得解决的问题？你怎么看？
